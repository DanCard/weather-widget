# Reduce Mocking in DailyViewHandlerTest.kt

## Context

`DailyViewHandlerTest.kt` has 1490 lines and 33 `mockk` references. Two categories of tests exist: pure-logic tests (mock-free) and integration `updateWidget` tests (Robolectric + mocking). The project philosophy is "no mocking framework — prefer pure function extraction" (from `arch/testing-strategy.md`). Currently only `mockk` is used because no pure-function extraction exists yet for some seams.

## Analysis

### Good mocking (keep as-is)

| Pattern | Lines | Rationale |
|---|---|---|
| `AppWidgetManager` mock + `slot<RemoteViews>` capture | 745, 792, 925, 957, 1247, 1302, 1345 | No alternative — Android framework class, can't instantiate without Robolectric. Capturing and applying `RemoteViews` to a real view hierarchy is a solid pattern. |

### Mocking that should be reduced

1. **`RainAnalyzer` mockkObject** (lines 67, 81, 105, 426, 462, 581)
   - Blanket `mockkObject(RainAnalyzer)` in `@Before` affects all 35 tests, but only 6 actually stub `getRainSummary`. The other 29 tests pay the cost of the mock setup/teardown for nothing.
   - The real `RainAnalyzer.getRainSummary` returns `null` for `emptyList()` inputs, so the `returns null` stubs are redundant.
   - **Better approach**: Inject a `rainSummaryProvider` lambda into `DailyViewLogic.prepareTextDays` and `prepareGraphDays` (defaulting to `RainAnalyzer::getRainSummary`). Test the rain-specific behavior with a lambda override, and let all other tests call the real function.

2. **`WorkManager` mockkStatic** (lines 1013, 1139)
   - Two tests verify enqueue side effects by mocking `WorkManager.getInstance()` and capturing `OneTimeWorkRequest` inputs.
   - Couples to implementation details (work spec inputs, string constants).
   - **Better approach**: Extract the "should I request a refresh?" decision into a pure function (similar to how `DailyViewLogic` was extracted from `DailyViewHandler`). The `requestMissingActualsRefresh`/`requestMissingDataRefresh` logic (lines 586–630 of `DailyViewHandler.kt`) is nearly extractable — `shouldRefreshMissingData` is already on `stateManager`, and the actual enqueue could be a thin wrapper. Test the *decision* (returning a reason string or null) directly, not the WorkManager dispatch details.

3. **`CurrentTemperatureResolver` mockkObject** (lines 1405–1459)
   - Test "DailyViewHandler uses provided lastObservedTemp" mocks `CurrentTemperatureResolver.resolve()` just to verify a parameter was passed through.
   - Proves wiring, not behavior. Fragile — breaks if resolver signature changes.
   - Also has a dead `WidgetStateManager` mock (lines 1389–1393) that is never injected — `updateWidget` creates its own internally.
   - **Better approach**: Remove this test. Test `CurrentTemperatureResolver.resolve()` directly with its own unit tests. If an integration test is needed to confirm `lastObservedTemp` threads through, call the real resolver with known inputs and assert on the displayed temperature in `RemoteViews`.

4. **Repeated mock setup boilerplate** in `updateWidget` tests
   - Each test repeats ~20 lines: `mockk<AppWidgetManager>`, `Bundle` setup, `every { ... } returns`, `slot<RemoteViews>()`, etc.
   - **Better approach**: Extract helper methods:
     ```kotlin
     private fun setupWidgetUpdate(appWidgetId: Int, widthDp: Int, heightDp: Int): Pair<AppWidgetManager, CapturedViews>
     ```
   - Reduces mock setup noise without reducing the mocking itself.

## Recommended Changes

### Change 1: Inject `rainSummaryProvider` lambda into DailyViewLogic

**File**: `app/src/main/java/com/weatherwidget/widget/handlers/DailyViewLogic.kt`

Add a defaulted lambda parameter to both `prepareTextDays` and `prepareGraphDays`:

```kotlin
rainSummaryProvider: (List<HourlyForecastEntity>, LocalDate, String?, LocalDateTime) -> String? = RainAnalyzer::getRainSummary
```

Replace direct `RainAnalyzer.getRainSummary(...)` calls with `rainSummaryProvider(...)`. No changes needed in `DailyViewHandler.kt` or other callers — they use the default.

### Change 2: Remove RainAnalyzer mocking from tests

**File**: `app/src/test/java/com/weatherwidget/widget/handlers/DailyViewHandlerTest.kt`

- Remove `mockkObject(RainAnalyzer)` from `@Before`
- Remove `unmockkObject(RainAnalyzer)` from `@After`
- Remove 5x `every { RainAnalyzer.getRainSummary(...) } returns null` — the real function returns null for `emptyList()` inputs
- Replace the `every { ... } answers { ... }` in the rain test (line 138) with a `rainSummaryProvider` lambda:
  ```kotlin
  rainSummaryProvider = { _, date, _, _ ->
      when (date) {
          today.plusDays(1) -> "9am"
          today.plusDays(2) -> "10am"
          else -> null
      }
  }
  ```
- Clean up unused imports (`mockkObject`, `unmockkObject`, `RainAnalyzer`)

### Change 3: Remove dead WidgetStateManager mock

Delete the `stateManager` mock and its 4 `every` stubs (lines 1389–1393) from the `DailyViewHandler uses provided lastObservedTemp` test. This mock is never injected — `updateWidget` creates its own `WidgetStateManager(context)` internally.

### Change 4: Restructure `lastObservedTemp` test to verify output

Instead of mocking `CurrentTemperatureResolver.resolve` and verifying it was called with the right parameter:
- Set up `AppWidgetManager` with proper dimensions (copy pattern from other `updateWidget` tests)
- Let the real `CurrentTemperatureResolver.resolve` run
- Capture `RemoteViews`, inflate, and assert the displayed current temperature reflects the provided `lastObservedTemp`
- Remove `mockkObject(CurrentTemperatureResolver)` and `unmockkObject(CurrentTemperatureResolver)`

### Change 5: Extract `updateWidget` test helper

Create a helper that sets up `AppWidgetManager` mock + widget options + `slot` capture:

```kotlin
private fun setupWidgetUpdate(appWidgetId: Int, widthDp: Int, heightDp: Int): Pair<AppWidgetManager, Slot<RemoteViews>>
```

Reduces ~20 lines of boilerplate per `updateWidget` test to ~3 lines.

### Change 6 (optional, lower priority): Extract refresh-decision pure function

Extract the "should I request a refresh?" decision from `requestMissingActualsRefresh`/`requestMissingDataRefresh` (lines 586–630 of `DailyViewHandler.kt`) into a testable pure function. Convert the two `WorkManager` mockkStatic tests to call this function and assert on the return value. Remove `mockkStatic(WorkManager::class)` and related teardown. This is lower priority because the current tests work and the extraction has touch-points across the handler.

## What stays

- `mockk<AppWidgetManager>()` in `updateWidget` tests — framework boundary, provides dimensions and captures RemoteViews
- `mockkStatic(WorkManager::class)` in 2 tests — system boundary for verifying work enqueueing (until Change 6 is done, if pursued)

## Net result

After Changes 1–5:
- 3 mock objects eliminated (`RainAnalyzer`, `CurrentTemperatureResolver`, `WidgetStateManager`)
- ~25 lines of mock setup/teardown removed
- 6 `every { ... }` stubs removed
- ~80 lines of boilerplate reduced via helper extraction
- Remaining mocks are justified framework/system boundaries

After Change 6 (if pursued):
- 1 more mock object eliminated (`WorkManager`)
- 2 more `mockkStatic`/`unmockkStatic` pairs removed
- Pure-logic coverage for refresh decisions
