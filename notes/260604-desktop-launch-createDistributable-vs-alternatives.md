# Desktop launch: is `createDistributable` obsolete? (2026-06-04)

## Context

While reducing desktop idle CPU (full session: 0.4% steady → ~0.1–0.2% intermittent),
the question came up of whether `./gradlew :desktop:createDistributable` is obsolete,
since the login autostart "references the project directory directly."

## The autostart chain (verified)

```
~/.config/autostart/weather-widget-desktop.desktop
  Exec= scripts/desktop-app-launcher-and-autostart.sh
        └─ exec's: desktop/build/compose/binaries/main/app/weather-widget-desktop/bin/weather-widget-desktop
                   └─ this binary IS the createDistributable output (jpackage launcher)
```

The running process was confirmed to be launched from that exact path. So "references
the project directory" is true — but that path is a **build output generated by
createDistributable**, not hand-written source. The autostart script even falls back to
running `createDistributable` if the binary is missing.

**Conclusion: createDistributable is not obsolete.** It is the only thing that produces
the binary autostart runs, and the only thing that translates `build.gradle.kts` changes
(including the `-XX` JVM flags) into the running process.

## Where the JVM flags actually live

The idle-CPU flags are NOT in the launcher binary. They are `java-options=` lines in:

```
desktop/build/compose/binaries/main/app/weather-widget-desktop/lib/app/weather-widget-desktop.cfg
```

That `.cfg` is regenerated only by `createDistributable` from the `jvmArgs` list in
`desktop/build.gradle.kts`. Relaunching the existing binary without rebuilding reads the
OLD `.cfg`, so build.gradle.kts edits never take effect. This is why the restart script
builds first.

Current flags (idle-CPU tuning):
- `-XX:+UseSerialGC` — drops G1's ~22 GC threads + the periodic G1 Service thread
- `-XX:-UsePerfData` — kills the 20 Hz hsperfdata sampler (the #1 idle waker)
- `-XX:+UnlockDiagnosticVMOptions` — required to set the two Guaranteed* flags below
- `-XX:GuaranteedSafepointInterval=0` — stops the 1 Hz idle safepoint
- `-XX:GuaranteedAsyncDeflationInterval=0` — stops the 1 s monitor-deflation timer

## Why "avoid createDistributable" is mostly not a good idea

### Option 1: autostart runs `./gradlew :desktop:run` — BAD for this app
- Resurrects a **Gradle daemon** (a second full JVM, hundreds of MB, its own periodic
  housekeeping) — directly contradicts the idle-CPU work that motivated this whole thread.
- `run` forks the app as a **child of the daemon**: two JVMs at login, coupled lifecycles.
- `CLAUDE.md` designates `run` as dev-only; the single-instance file lock exists
  specifically to stop a stray `:desktop:run` from spawning a duplicate Dorkbox tray.

### Option 2: direct `java -cp … MainKt` from `desktop/build` output — WORKABLE, LOW ROI
- Avoids jlink/jpackage and the daemon (one JVM, system JDK, flags on the command line).
- But it does **not** avoid building — still needs `:desktop:classes`/`:desktop:jar` to
  compile on every code change. It only skips jlink/jpackage, which when up-to-date is the
  ~7 s no-op pass, not the slow part.
- You inherit bundling that jpackage does for free: `-Dskiko.library.path`,
  `-Dcompose.application.resources.dir`, and the curated `modules(java.sql, jdk.crypto.ec,
  jdk.unsupported, …)`. A hand-rolled classpath launcher has to handle Skiko native-lib
  extraction and the resources dir itself — and it breaks only at launch, not under `run`.

### Key correction
The premise has the causality backwards: the project-directory binary autostart runs
*is the output of* createDistributable. The flags can't escape the build either — they're
declared in `build.gradle.kts` and only become `java-options=` in the `.cfg` when
createDistributable regenerates it. "Skipping the build" just relocates the flags into a
shell script; it doesn't make the build redundant.

## The actual goal: quick restarts without the createDistributable step

The motivation was fast restarts, not removing the packaging concept. Resolution:

- `createDistributable` is **already incremental** — when classes are unchanged it's a
  ~7 s up-to-date pass, not a re-jlink.
- For a restart that does **not** need to pick up code/flag changes, the build is genuinely
  unnecessary: just kill + relaunch the existing repo binary. That's instant.
- → Added `scripts/desktop-fast-restart-no-rebuild.sh`: kill running instances + relaunch the existing
  distributable via the autostart launcher, **no Gradle build**. Use it for plain restarts;
  use `scripts/desktop-full-rebuild-and-restart.sh` when you changed code or `build.gradle.kts`.

### Recommended split (matches CLAUDE.md intent)
- autostart / daily use → `createDistributable` output (one JVM, bundled natives, declarative flags)
- plain restart, no code change → `desktop-fast-restart-no-rebuild.sh` (no build)
- active development / fast loops → `./gradlew :desktop:run` (dev-only, not wired into login)
